# 需求单 SOP 提炼

> 来源：`data\SOP\sop1.jpg` ~ `sop5.jpg`，并参考 `data\SOP\GPT建议.txt`。
> 用途：后续撰写需求单时的格式、语言和检查标准。

## 1. 总体定位

需求单应描述“业务/系统逻辑变更”，不是代码实现方案。

撰写重点：

- 数据来源
- 判断逻辑
- 处理逻辑
- 输出结果
- 预期效果
- 涉及系统之间的交互关系

禁止把需求单写成：

- 程序代码
- SQL / 数据库脚本
- 接口实现代码
- 纯技术实现细节

## 1.1 工程化表达 / 降低 AI 感

最终 Word 交付前，需按 `docs\需求单工程化降AI风格规则.md` 做一轮后处理。

处理原则：

- 直接描述修改点，少写目的型解释。
- 删除“本需求旨在”“综上所述”“通过……从而……”等 AI 感句式。
- 保留字段、表名、判断条件、输出结果和 `【待确认】`。
- 允许 `NOTE`、`TBD`、`需制造确认` 等工程备注。
- 不新增逻辑、不补待确认字段。

## 1.2 事实来源与变更基线

需求知识稿、历史交付物和案例是参考基线，不是所有新需求的唯一事实来源。新需求可能有意新增、修改或删除旧逻辑。

撰写前先按 [[30.areas/requirement-writing/01_SOP/需求事实来源与变更基线规则.md]] 区分：

- 当前线上实际逻辑。
- 历史文档记录的逻辑。
- 本次需求声明的目标逻辑。
- 明确保持不变和不在本次范围的内容。
- 尚未确认的冲突。

新稿与旧稿不一致时，先建立冲突清单，不直接判定任一版本错误，也不自动用旧知识覆盖新需求。

## 2. 首页基础信息

需求单首页顶部需包含基础信息表：

- 编号：由信息技术部填写
- 类别：软件采购 / 硬件采购 / 功能开发 / 工程及服务
- 申请部门
- 系统名称：类别为“功能开发”时必填，例如 CIM 计算机集成制造系统 Fab6（二科）
- 申请人员
- 功能模块：类别为“功能开发”时必填，例如 智能派工系统（RTD/DSP）
- 申请日期
- 希望交付期

## 3. 标准结构

### 3.1 项目简介和必要性分析

需说明：

- 项目背景：当前业务背景是什么。
- 存在问题：当前逻辑或流程存在什么问题。
- 需求目标：希望达到什么效果。
- 改善方案概述：准备如何实现该需求。

写作要求：

- 标题使用宋体五号、两端对齐。
- 内容使用宋体五号，首行缩进 2 字符。
- 表述应说明“为什么要做该需求、如何实现、实现后达到什么效果”。

### 3.2 项目投资方案比较及效果分析

需包含：

- 改善方案：说明需求涉及的系统交互，例如 MES / RTD / AMA / CIM / EAP 等系统之间的作用和参数交互。
- 效果分析：收益需尽量量化。

效果分析示例：

- 减少人工操作 X 小时/天
- 自动化率提升 X%
- 减少异常派工 Case
- 缩短 Lot 等待时间 X 分钟
- 品质优化 / 设备效率提升

### 3.3 需求流程图

对于逻辑较复杂的需求，必须增加需求流程图。

流程图建议结构：

```text
开始
↓
数据获取
↓
条件判断
├─ 是 → 执行逻辑 A
└─ 否 → 执行逻辑 B
↓
结果输出
↓
结束
```

注意：

- 流程图内容不固定，应根据需求逻辑绘制。
- 判断节点要能对应正文逻辑。
- 复杂分支需保证“是/否”路径清晰。

## 4. 标题层级规范

一级标题：

```text
1. Report 部分
```

要求：

- 宋体五号
- 加粗
- 两端对齐

二级标题：

```text
1.1 二级标题
```

要求：

- 标题应简洁说明该部分逻辑方向，例如：计算 / 新增 / 修改 / 删除
- 宋体五号
- 加粗
- 两端对齐

三级标题：

```text
1.1.1 三级标题
```

要求：

- 宋体五号
- 加粗
- 首行缩进 2 字符

四级条目：

```text
（1）（2）（3）……
```

如需细分，可使用：

```text
① ② ③ ④ ⑤……
```

## 5. 正文写作规范

### 5.1 参数来源必须明确

参数拿取需说明：

- 系统 / 数据库
- 表名称
- 对应栏位
- 获取条件
- 获取方式

推荐写法：

```text
通过表 mesprod.fwlot / mesprod.fablotext，拿取 processingstatus in（'Active','Hold'）的 appid 及对应 priority、internalpriority 信息。
```

禁止模糊写法：

```text
系统获取 Lot 信息。
```

### 5.2 专有名词首次出现必须解释

第一次出现的专有名词、缩写、内部对象名，需要解释含义，或在括号内说明。

示例：

```text
OQT（Over QueueTime）
Pirun（Pilot Run）
```

如果名称含义不确定，撰写前应向用户确认。

### 5.3 使用逻辑语言，不写模糊判断

应把自然语言转换成明确逻辑。

推荐写法：

```text
若条件 A 成立，则执行逻辑 B；否则执行逻辑 C。
```

```text
当条件 A 满足时，执行逻辑 B；当条件 A 不满足时，执行逻辑 C。
```

避免使用：

- 大概
- 可能
- 应该
- 预计
- 尽量

### 5.4 复杂逻辑必须配示例

当表述逻辑较复杂时，需增加举例说明；举例必须与对应逻辑一致，方便评审理解。

示例可采用表格：

| Group | ID | ActualLendFOUPCount | GroupActualLendFOUPCount |
| --- | --- | --- | --- |
| 1 | 1 | 3 | 5 |
| 1 | 2 | 2 | 5 |
| 2 | 3 | 4 | 4 |

## 6. 详细逻辑章节层级

从 SOP 图片格式看，详细逻辑的大章节主要按系统/执行模块划分：

- 一、RTD 部分更改逻辑
- 二、AMA 部分更改逻辑

`Rule`、`UI`、`Report` 不是默认与 RTD / AMA 平级的大章节，而是根据需求内容放在 RTD 或 AMA 大章节下的小节。

推荐层级：

```text
一、RTD 部分更改逻辑
1. 参数获取逻辑
1.1 Lot 信息获取
1.2 Priority 计算
2. 涉及 Rule 相关的逻辑
3. 涉及 UI 配置相关的逻辑
4. 涉及生成存 Report 相关的逻辑

二、AMA 部分更改逻辑
1. 执行频率
1.1 数据获取
1.2 条件判断
1.3 执行动作
2. 涉及 UI 配置相关的逻辑
3. 涉及生成存 Report 相关的逻辑
```

实际撰写时，只保留与本次需求相关的小节。

## 7. RTD 部分变更逻辑

RTD 需求可采用以下结构：

```text
一、RTD 部分更改逻辑

1. 一级标题
1.1 二级标题
1.1.1 三级标题
```

每个 RTD 逻辑章节建议包含：

- 数据来源
- 判断逻辑
- 处理逻辑
- 输出结果
- 异常处理

示例章节：

- 参数获取逻辑
- 分组逻辑
- 排序逻辑
- 派工逻辑
- 异常处理逻辑

### 7.1 Rule 相关逻辑

涉及 RTD Rule 时，作为 RTD 大章节下的小节说明：

- Rule 名称
- 插入位置：在哪个判断 / 哪段逻辑之后新增
- Sorting 逻辑
- Reason 逻辑
- Dispatch 逻辑
- 指标优先级

优先级必须明确。

示例：

```text
1 > 0 > 空
```

或：

```text
High > Medium > Low
```

### 7.2 RTD 下的 UI 配置逻辑

涉及 RTD UI 配置时，作为 RTD 大章节下的小节说明，要求见“UI 配置部分”。

### 7.3 RTD 下的 Report 逻辑

涉及 RTD Report 时，作为 RTD 大章节下的小节说明，要求见“Report 部分”。

## 8. AMA 部分变更逻辑

涉及 AMA 时，格式与 RTD 保持一致，并必须说明执行频率。

示例：

```text
AMA 每 5 分钟执行一次。
```

建议结构：

- 执行频率
- 数据获取
- 条件判断
- 执行动作
- 输出结果

AMA 下如涉及 UI 或 Report，也应作为 AMA 大章节下的小节展开。

## 9. UI 配置部分

涉及 UI 时必须说明。UI 小节应放在对应的 RTD 或 AMA 大章节下，不默认单独作为一级大章节：

- 需要拿取的 UI / 信息
- 是否必填
- 是否支持模糊匹配
- 是否新增 UI
- UI 操作逻辑

配置项建议使用表格：

| 配置项 | 是否必填 | 是否支持模糊匹配 | 说明 |
| --- | --- | --- | --- |
| Source | 非必填 | 支持 | 说明配置来源 |
| TargetFOUPCarrierType | 非必填 | 支持 | 说明目标 FOUP Carrier Type |
| LotTech | 非必填 | 支持 | 说明 Lot 技术别 |
| Product | 非必填 | 支持 | 说明产品信息 |

UI 操作逻辑需说明：

- 支持新增、删除、修改
- 相同配置已存在时是否禁止新增
- 字段为空、重复、格式错误时如何处理

## 10. Report 部分

涉及生成 / 保存 Report 时，需说明。Report 小节应放在对应的 RTD 或 AMA 大章节下，不默认单独作为一级大章节：

- Report 名称或信息格式
- Report 存取频率，例如 5min/次
- Report 栏位信息
- 每个栏位的简要说明

示例：

```text
Report 栏位信息：LotID、Priority、DispatchTime。

LotID：Lot 唯一标识。
Priority：派工优先级。
DispatchTime：派工时间。
```

## 11. 原逻辑与现逻辑对比

涉及逻辑变更时，必须增加：

```text
原逻辑：
……

现逻辑：
……

修改原因：
……
```

## 12. 审批意见区

需求单末尾保留审批意见区：

- 申请部门意见 / 日期
- 申请部门分管领导意见 / 日期
- 相关部门意见 / 日期
- 相关部门分管领导意见 / 日期
- 信息技术部意见 / 日期
- 信息技术部分管领导意见 / 日期
- 附件名称

## 13. 输出检查清单

撰写完成后检查：

- [ ] 是否按基础信息、项目简介、方案与效果、流程图、详细逻辑、审批区组织。
- [ ] 是否说明涉及系统及系统间交互。
- [ ] 是否说明数据来源、表名、栏位、获取条件。
- [ ] 是否用“若 A，则 B；否则 C”表达判断逻辑。
- [ ] 是否解释首次出现的专有名词。
- [ ] 复杂逻辑是否有流程图或表格示例。
- [ ] 涉及 UI 时是否有配置表和操作逻辑。
- [ ] 涉及 Report 时是否有频率、栏位、栏位说明。
- [ ] 涉及 Rule 时是否说明插入位置和优先级。
- [ ] 涉及 AMA 时是否说明执行频率。
- [ ] 效果分析是否尽量量化。
