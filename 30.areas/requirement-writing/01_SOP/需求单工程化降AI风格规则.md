# 需求单工程化降 AI 风格规则

> 来源：用户提供的 DSP-Humanizer 建议，已结合需求单 SOP 提炼。  
> 用途：生成最终 Word 前，对需求单做最后一轮表达后处理。

## 定位

该规则不是重新设计需求，也不是补逻辑。

只做：

```text
AI 说明稿 → 内部工程变更说明
```

适用文档：

- 需求申请单
- Test Case
- Release Note
- 内部逻辑说明
- Rule / Sorting / Report 修改说明

## 保留内容

后处理时必须保留：

- 表名、字段名、参数名。
- Rule / Sorting / Report / UI / DB 修改点。
- 判断条件。
- 输出结果。
- 异常与边界。
- `【待确认】`。
- 制造 / IT 需确认事项。

## 删除或弱化内容

优先删除：

- “本需求旨在……”
- “为了……从而……”
- “综上所述……”
- “通过该优化可以有效提升……”
- 重复解释系统背景。
- 教科书式介绍 RTD / AMA / QZone。
- 每段都写原因、目的、意义。

## 推荐写法

### 目的句改动作句

修改前：

```text
本需求旨在优化 LoadingBalance 计算逻辑，以提升跨厂 WIP balance 判断准确性。
```

修改后：

```text
调整 LoadingBalance 计算粒度，由 SelfCapability 改为机台维度。
```

### 长解释改变更说明

修改前：

```text
由于不同产品、不同 Lot 在可作业机台方面存在差异，因此需要通过机台维度计算方式，使系统能够更准确反映现场实际情况。
```

修改后：

```text
不同 Lot 可作业机台存在差异，Loading 改按机台维度计算。
```

### 总结句改结果句

修改前：

```text
综上所述，本次优化能够有效提升系统判断准确性。
```

修改后：

```text
本次修改作用于 EqpLoadingSummary 计算逻辑。
```

## 允许的工程备注

可直接保留：

```text
NOTE:
TBD:
当前不包含：
本次暂不调整：
需制造确认：
需 IT 确认：
依赖 MES 状态：
```

## 不允许的处理

- 不新增需求。
- 不补充用户没确认的逻辑。
- 不把 `【待确认】` 改成确定描述。
- 不删除关键边界。
- 不删除影响范围。
- 不为了自然表达牺牲准确性。

## 最终检查

生成 Word 前检查：

- [ ] 是否仍符合需求单 SOP 表头和章节结构。
- [ ] 是否删除明显 AI 句式。
- [ ] 是否比初稿更像变更说明，而不是论文说明。
- [ ] 字段、表名、判断条件是否完整保留。
- [ ] 待确认事项是否仍保留。
