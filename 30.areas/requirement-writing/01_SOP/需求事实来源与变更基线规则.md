# 需求事实来源与变更基线规则

## 核心原则

知识库中的需求稿、历史交付物、OCR 和案例都是参考证据，不天然代表当前正确逻辑，也不能作为所有新需求的唯一事实来源。

新需求可能是在修正、替换或删除旧逻辑。新稿与旧稿不一致时，先判断这是“有意变更、表述错误、历史资料错误，还是现场逻辑已经变化”，不得直接用旧知识覆盖新需求，也不得仅凭新稿就删除历史依据。

统一入口用于导航和版本管理，不等于统一事实裁决。

## 四类输入

| 输入类型 | 作用 | 使用限制 |
|---|---|---|
| 本次需求声明、会议结论、用户确认 | 描述本次目标逻辑 | 未确认细节继续标记 `【待确认】` |
| 线上系统行为、数据、配置和接口结果 | 证明当前实际逻辑 | 需记录采集时间、环境和范围 |
| 历史需求单、交付物、知识稿 | 提供历史基线和设计背景 | 可能过期、错误或将被本次需求修改 |
| OCR、截图、转述和推断 | 提供线索 | 未回看原始证据前不得写成确定事实 |

不存在适用于所有字段的固定优先级。应分别确认“当前实际逻辑”和“本次目标逻辑”。

## 新需求开始时

先建立本次变更声明：

```text
本次新增：
本次修改：
本次删除：
明确保持不变：
不在本次范围：
待确认：
```

再将历史资料作为对照基线，生成冲突清单：

| 逻辑项 | 历史基线 | 本次声明 | 冲突类型 | 确认状态 | 确认方 |
|---|---|---|---|---|---|
|  |  |  | 有意变更 / 表述差异 / 待核实 | 待确认 |  |

## 冲突处理

1. 新稿与旧稿不同，不能直接判定新稿错误。
2. 旧稿与线上行为不同，不能直接判定线上实现正确；需确认是文档过期、实现偏差还是临时配置。
3. 用户明确声明为本次变更的内容，作为目标逻辑候选；影响范围、边界和异常路径仍需补齐。
4. 未在本次需求中提及的旧逻辑，只有在明确标记“保持不变”后才能自动继承。
5. 冲突未关闭前使用“工作稿 / 评审稿”，不使用“最终版”。

## 形成可交付版本

只有同时满足以下条件，某个版本才能标记为本次需求的确认基线：

- 本次新增、修改、删除和不调整范围已经列明。
- 当前逻辑与目标逻辑已经分开描述。
- 关键冲突已由对应责任方确认。
- 待确认项已关闭，或明确允许带待确认进入评审。
- Markdown、Word和流程图使用同一版业务口径；独立 Test Case Excel 明确记录其依据的需求单版本。
- 项目 README 记录版本状态、确认日期和适用范围。
