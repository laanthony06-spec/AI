# DSP Humanizer Prompt

> 用途：作为需求单、Test Case、Release Note、内部逻辑说明的最终后处理层。  
> 目标：降低 AI 生成感，使文本更接近半导体厂 DSP 工程师内部文档风格。  
> 注意：本 Prompt 只改表达方式，不补充逻辑、不新增需求、不推理未确认信息。

## 使用时机

在完成以下步骤后使用：

```text
需求分析 → 逻辑设计 → 需求单草稿 → Review → Humanizer 后处理
```

不要在逻辑尚未确认时使用 Humanizer。否则容易把“不完整逻辑”压得更隐蔽。

## 处理目标

将结构化、解释型、AI 感较强的文本，转换为：

- 工程中性；
- 偏变更说明；
- 直接描述修改点；
- 保留必要字段、规则、边界；
- 允许 `NOTE`、`TBD`、`需确认` 等工程备注；
- 比原文减少约 20%~40% 的重复解释。

## 需要削弱的 AI 风格

- “本需求旨在……”
- “为了提升……，因此……”
- “综上所述……”
- “通过……从而……”
- 过度完整的五段式解释。
- 每个小节都写背景、原因、目的、预期收益。
- 教科书式介绍系统原理。
- 大量“首先 / 其次 / 最后 / 综上”。

## 需要增强的工程风格

- 直接写 `新增 / 修改 / 删除 / 调整 / 维持 / 输出`。
- 优先保留 Rule change、Logic change、System impact、Edge case。
- 对未确认内容直接写 `【待确认】` 或 `需制造确认`。
- 对外部依赖直接写 `Depends on MES behavior` / `依赖 MES 状态`。
- 可保留局部不完整信息，不强行补成完整闭环。

## 转换规则

### 1. 目的型开头改成动作型开头

不推荐：

```text
本需求旨在优化 LoadingBalance 计算逻辑，以提升跨厂 WIP balance 判断准确性。
```

推荐：

```text
调整 LoadingBalance 计算粒度，由 SelfCapability 改为机台维度。
```

### 2. 删除重复解释，只保留事实

不推荐：

```text
由于不同产品在可作业机台上存在差异，因此需要通过机台维度计算方式，使系统能够更准确反映现场实际情况。
```

推荐：

```text
不同 Lot 可作业机台存在差异，Loading 改按机台维度计算。
```

### 3. 总结句只保留必要结论

删除：

```text
综上所述，本次优化能够有效提升系统判断准确性。
```

保留：

```text
本次修改作用于 EqpLoadingSummary 计算逻辑。
```

### 4. 不解释系统常识

若读者是 DSP / IT / 制造内部人员，不解释 RTD、AMA、QZone 的基础定义，除非需求本身要求说明。

### 5. 保留工程备注

允许使用：

```text
NOTE:
TBD:
当前不包含：
本次暂不调整：
需制造确认：
需 IT 确认：
依赖 MES 状态：
```

### 6. 不改变 SOP 大结构

公司需求单仍需保留 SOP 要求的大章节和表头。Humanizer 只调整段落表达，不删除必要章节。

## 输出检查清单

- [ ] 是否删除了“本需求旨在 / 通过……从而……”等 AI 句式。
- [ ] 是否保留所有字段、表名、判断条件和输出结果。
- [ ] 是否没有新增未经用户确认的逻辑。
- [ ] 是否把解释型段落压成变更说明。
- [ ] 是否保留 `【待确认】`，没有擅自补全。
- [ ] 是否仍符合公司 SOP 结构。

## 禁止行为

- 不新增需求。
- 不补充缺失逻辑。
- 不把 `【待确认】` 改成确定表述。
- 不删掉边界条件、异常场景、影响范围。
- 不为了“自然”而牺牲准确性。
